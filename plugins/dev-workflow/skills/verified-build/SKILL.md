# verified-build

모델 한 번의 호출 능력은 올릴 수 없지만, 시스템의 결과물 품질은 올릴 수 있다. 이 스킬은 능력 격차를 **탐색량 × 검증기**로 메운다: 여러 독립 시도를 만들고, 실행 가능한 테스트와 "깨뜨리려는" 검증자로 걸러내고, 살아남은 것만 적용한다.

검증기가 천장이다. 테스트로 옳고 그름을 판정할 수 있는 작업에서만 효과가 있다. 판정 기준이 취향인 작업(문구, 디자인)에는 맞지 않으니, 그런 요청이면 이 스킬을 쓰지 말고 평소대로 진행한다.

## 실행 전 확인 (직접, 워크플로 호출 전에)

워크플로 에이전트들은 격리된 git worktree에서 일하고 커밋 SHA로 결과를 주고받는다. worktree는 HEAD에서 만들어지므로 아래를 먼저 확인한다. 이걸 건너뛰면 에이전트 십여 개가 헛돈다.

1. **git 저장소인가**: `git rev-parse --is-inside-work-tree`. 아니면 사용자에게 알리고 아래 "git 없이" 절차로 대체한다.
2. **커밋 안 된 변경이 있는가**: `git status --short`. 있으면 worktree에는 그 변경이 없다는 점을 사용자에게 알리고, 먼저 커밋할지 그대로 진행할지 묻는다. 임의로 stash 하거나 커밋하지 않는다.
3. **테스트 명령**: package.json scripts, Makefile, CI 설정, README에서 찾아 한 번 실행해 본다. 현재 상태에서 이미 실패하는 테스트가 있으면 사용자에게 보고한다(기준선이 빨간색이면 검증자가 구현 탓으로 오판한다). 테스트 인프라가 전혀 없으면 멈추고, 테스트 러너부터 설정할지 묻는다.
4. **작업 범위**: 요청이 서로 무관한 여러 작업이면 나눠서 작업마다 한 번씩 실행한다. 한 번의 실행은 하나의 검증 가능한 변경을 다룬다.

## 워크플로 호출

이 스킬 호출 자체가 다중 에이전트 실행에 대한 사용자의 동의다. Workflow 도구를 다음과 같이 호출한다:

- `scriptPath`: 이 스킬 디렉터리의 `workflow.js` 절대 경로
- `args`: JSON 객체(문자열로 감싸지 않는다)

```json
{
  "task": "사용자 요청을 구체적으로. 관련 파일, 제약, 사용자가 말한 완료 기준 포함",
  "testCommand": "npm test",
  "attempts": 3,
  "maxRepairRounds": 2,
  "apply": true
}
```

| 인자 | 기본값 | 의미 |
|---|---|---|
| `task` | 필수 | 작업 설명. 대화에서 정해진 결정·제약을 빠짐없이 옮긴다. 에이전트는 이 대화를 보지 못한다 |
| `testCommand` | 자동 탐색 | 위에서 확인한 명령을 넣는다 |
| `attempts` | 3 | 병렬 구현 개수(1~6). 어려운 작업일수록 올린다 |
| `maxRepairRounds` | 2 | 후보당 수정 재시도 횟수 |
| `apply` | true | false면 검증만 하고 작업 트리에 적용하지 않는다 |

비용은 대략 에이전트 `2 + attempts × (2 ~ 2 + 2 × maxRepairRounds) + 2`개다. 기본값이면 10~22개. 실행 전에 이 규모를 한 줄로 알린다.

## 파이프라인이 하는 일

| 단계 | 내용 | 이유 |
|---|---|---|
| Spec | 요청을 관찰 가능한 완료 기준과 서로 다른 접근 N개로 변환 | 모호함을 구현 전에 제거 |
| Tests | 접근을 모르는 별도 에이전트가 명세만 보고 실패하는 테스트 작성 | 구현자가 자기 오해를 테스트에 복제하지 못하게 |
| Attempt | 접근마다 격리된 worktree에서 구현, 테스트 수정 금지 | 같은 프롬프트 반복보다 접근 분산이 탐색 효과가 큼 |
| Check | 다른 에이전트가 테스트 재실행 + 반례를 직접 실행해 찾음 | 자기 보고를 믿지 않음. 재현된 결함만 인정 |
| Repair | 실패 출력 원문을 받아 근본 원인 수정 후 재검증 | 요약된 에러는 정보를 잃음 |
| Select | 살아남은 후보 중 코드베이스 적합성·단순성 기준 선택 | |
| Apply | 승자를 작업 트리에 미커밋 상태로 적용, 테스트 재실행 | 사용자가 검토 후 직접 커밋 |

## 결과 처리

워크플로 반환값의 `status`에 따라:

- **`applied_and_passing`**: `git diff`로 실제 변경을 직접 확인한 뒤 보고한다. 에이전트 보고는 증거가 아니다. 승자의 접근, 선택 이유, 탈락한 후보와 그 이유, 잡아낸 결함 수를 알린다. 커밋은 사용자가 요청할 때만 한다.
- **`verified_but_apply_failed`**: `applied.problem`을 그대로 전한다. 보통 사용자의 미커밋 변경과 충돌한 경우다. 승자 SHA(`winner.sha`)가 남아 있으니 사용자 결정 후 수동 적용할 수 있다.
- **`verified_not_applied`**: `apply: false`로 실행한 경우. 승자 SHA와 `git diff <baseSha> <sha>` 확인 방법을 알린다.
- **`no_verified_candidate`**: 아무것도 적용되지 않았다. 후보별 마지막 검증 결과(`candidates[].lastCheck`)를 읽고 공통 실패 원인을 찾는다. 모든 후보가 같은 테스트에서 실패하면 테스트나 명세가 틀렸을 가능성이 높으니 그 테스트를 직접 읽어 본다. 원인을 사용자에게 보고하고, 명세를 고쳐 재실행할지 묻는다. 통과한 것처럼 꾸미지 않는다.

`spec.openQuestions`가 있으면 가정한 내용을 사용자에게 반드시 전한다. 가정이 틀렸다면 결과 전체가 틀린 것이다.

임시 태그 `vb-tmp-*`는 Apply 단계가 지운다. Apply가 실행되지 않았으면 남아 있으니, 사용자가 후보를 더 볼 필요가 없을 때 `git tag -l "vb-tmp-*"`로 확인 후 삭제한다.

## 실패 패턴 축적

`defectsFound`에는 검증자가 잡아낸 결함이 후보·라운드별로 들어 있다. 여러 후보에서 같은 종류의 결함이 반복됐다면(예: 빈 입력 처리 누락, 특정 모듈의 관례 위반) 그 패턴을 한두 줄로 요약해 프로젝트 CLAUDE.md에 추가할지 사용자에게 제안한다. 이 축적이 다음 실행의 첫 시도 품질을 올리는 유일한 경로다. 한 번만 나온 결함은 기록하지 않는다.

## git 없이

worktree 격리가 불가능하므로 워크플로를 쓰지 않고 같은 원칙을 순차로 적용한다:

1. 완료 기준을 목록으로 적고 사용자에게 확인받는다.
2. 구현 전에 테스트를 먼저 작성하고 실패를 확인한다.
3. 구현한다.
4. 서브에이전트 하나에 명세와 결과물만 주고(구현 과정 맥락 없이) 깨뜨려 보라고 한다. 재현된 결함만 받는다.
5. 실패 출력 원문으로 수정하고 4번을 반복한다.

병렬 시도가 없으므로 효과는 줄어든다는 점을 사용자에게 알린다.
